# DAY 13 — FastAPI + PostgreSQL Employee Management API

## 1. Project Overview

The **Employee Management API** is a RESTful backend application developed using **FastAPI, SQLAlchemy, and PostgreSQL**.

The purpose of this project is to extend the Day 12 Employee REST API by replacing temporary in-memory storage with a **real PostgreSQL database**.

The application provides complete employee management functionality including:

* Create Employee
* Read Employee
* Read All Employees
* Update Employee
* Partial Update using PATCH
* Delete Employee
* Search Employee by name
* Filter Employees by department
* Request validation
* Database-level constraints
* Duplicate data detection
* HTTP error handling
* Transaction management
* Automatic PostgreSQL table creation
* Interactive Swagger API documentation


# 2. Objective

The main objective of Day 13 is to connect the FastAPI application to a real relational database and implement persistent employee data storage.

# 4. Key Features

## 4.1 Create Employee

Creates a new employee and stores the employee record in PostgreSQL.
http
POST /employees


Example request:

json
{
  "employee_name": "Rahul Kumar",
  "email": "rahul@gmail.com",
  "phone": "9876543210",
  "salary": 55000,
  "joining_date": "2025-06-10",
  "department": "IT",
  "designation": "Software Engineer"
}


The employee ID is automatically generated by PostgreSQL.


## 4.2 Read All Employees

Returns all employees stored in PostgreSQL.

http
GET /employees



## 4.3 Read Employee by ID

Returns a specific employee using the employee ID.
http
GET /employees/{employee_id}


Example:

http
GET /employees/1


If the employee does not exist, the API returns:

text
404 Not Found




# 5. Search Functionality

The API supports searching employees by name.

http
GET /employees?search=rahul


The search uses a case-insensitive database query.

Examples:

text
GET /employees?search=rahul
GET /employees?search=Rahul
GET /employees?search=RAHUL


The search can return employees whose names contain the provided search term.



# 6. Department Filtering

Employees can be filtered by department.

http
GET /employees?department=IT


Example:

http
GET /employees?department=HR


The API returns only employees belonging to the requested department.


# 7. Combined Search and Filtering

Search and department filtering can also be used together.

Example:

http
GET /employees?department=IT&search=rahul


This allows the API to return employees who match both conditions.



# 8. Update Employee

The API supports updating employee information.

http
PUT /employees/{employee_id}


Example:

json
{
  "employee_name": "Rahul Kumar",
  "email": "rahul.updated@gmail.com",
  "phone": "9876543210",
  "salary": 65000,
  "joining_date": "2025-06-10",
  "department": "IT",
  "designation": "Senior Software Engineer"
}



# 9. Partial Update using PATCH

The API supports partial updates using the HTTP PATCH method.

http
PATCH /employees/{employee_id}


Example:

json
{
  "salary": 75000
}


Only the provided field is updated.

Existing employee information remains unchanged.

This demonstrates the difference between:


PUT   → Full update
PATCH → Partial update




# 10. Delete Employee

Employees can be removed from PostgreSQL.

http
DELETE /employees/{employee_id}

Example:
http
DELETE /employees/4


Successful response:

json
{
  "message": "Employee with ID 4 deleted successfully"
}



# 11. Data Validation

The API performs request validation using Pydantic.

Validation includes:

### Employee Name

* Required
* Minimum length: 2 characters
* Maximum length: 100 characters
* Empty values are rejected

### Email

* Required
* Must be a valid email address
* Must be unique

### Phone

* Required
* Must contain only digits
* Must contain 10–15 digits
* Must be unique

### Salary

* Required
* Must be greater than zero

### Joining Date

* Required
* Cannot be a future date

### Department

* Required
* Minimum length: 2 characters
* Maximum length: 100 characters

### Designation

* Required
* Minimum length: 2 characters
* Maximum length: 100 characters

Invalid requests are rejected by FastAPI with appropriate validation responses.

# 14. Transaction Management

Database write operations use transactions.

For successful operations:

```python
db.commit()
```

For failed operations:

```python
db.rollback()
```

The project uses rollback handling to prevent failed database operations from leaving the database session in an inconsistent transaction state.

Example:

```python
try:
    db.add(employee)
    db.commit()
    db.refresh(employee)

except Exception:
    db.rollback()
    raise
```

# 18. Environment Configuration

Database credentials are stored in `.env`.

Example:

env
DATABASE_URL=postgresql+psycopg://postgres:YOUR_PASSWORD@localhost:5432/employee_management


The `.env` file must not be committed to GitHub because it contains database credentials.

A `.env.example` file can be used to document the required environment variable without exposing credentials.
